# Contributing to Commons FinOps

Thanks for being here. This repository is documented practice from running the financial and operations function of a 501(c)(3) fiscal sponsor for digital governance research. It is meant to compound across many practitioners, not stay locked to one.

If you operate a fiscal sponsor, a foundation, a sponsored project, an OSS funding core, or a polycentric institution, your contribution is valuable.

## What kind of contribution helps

1. **Corrections**: If something here is factually wrong, regulatorily inaccurate, or inconsistent with current practice, open a PR or an issue with the specific reference.
2. **Extensions**: If there is a topic this repo should cover and does not, propose it. Especially welcome: jurisdiction-specific audit thresholds, current 990 schedule requirements, treasury controls for new asset classes, software stack comparisons.
3. **Templates**: The `templates/` folder is reserved for operational artifacts (intake checklists, chart of accounts shapes, sanctions schedules, conflict resolution paths) that operationalize the methodology. Contribute templates that have been battle-tested in a real organization, with a note on where they were used.
4. **Case studies**: Year one experience from your own fiscal sponsor, foundation, or sponsored project. Anonymized where needed. The Metagov case study in this repo is a template for the shape.
5. **Translations**: Into other languages, or into adjacent governance frames (commons theory, polycentric models, OSS funding, civic tech, AI safety, climate, privacy tech, open science).

## How to contribute

### Small changes (typos, clarifications)

Open a pull request directly. Title it clearly. Describe what you changed and why.

### Substantive changes (new sections, methodological revisions)

Open an issue first. Describe what you want to add and why. We can have the design conversation before you spend time writing.

### New templates

Open an issue describing the template and the operating context it came from. We will discuss naming, scope, and where it belongs in the repo.

### Case studies

Open an issue first. Case studies are most useful when they describe specific operational decisions, the principles behind them, and the outcomes. Anonymize identifying details if the institution requests it.

## Style

- Direct, operator from the seat tone. Not coaching or consulting language.
- Concrete examples over generic principles where possible.
- Cite real organizations and real practices by name where appropriate.
- Avoid em dashes. Use periods, commas, semicolons, colons, parentheses.
- Where you reference numbers (grant sizes, audit thresholds, fees, etc.), source them and note your source.
- Where you reference regulations (FASB ASU, IRS Form, state requirements), cite the actual rule and link to it.

## Review

Pull requests are reviewed for accuracy, scope, and fit. Substantive contributions may include a brief conversation about how to integrate them. The intent is to keep this resource trustworthy as a reference.

## Code of conduct

Be useful. Be specific. Respect the time of the people who run these organizations. Disagree with ideas, not with people. If a contribution surfaces a structural issue at a real organization, do not name individuals who would be embarrassed.
